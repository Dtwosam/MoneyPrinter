# Printer V1 V2-9.8B — Historical Dual-Artifact-Root Repair Design

## Verdict

`V2_9_8B_HISTORICAL_DUAL_ARTIFACT_ROOT_REPAIR_DESIGN_PASS_PENDING_EXACT_APPLICATION_ROOT_BINDING`

## Baseline and classification

- Baseline: `7df997f79547355a52f26caef48e112586eabaf1`
- Historical execution: `20260814T172224Z-490856f405bf`
- Authoritative DB remains unchanged at SHA `5e830af41d58325d3f9e521f1b95f697b8151113cb783cf05a2a776e204639bc`.
- Blocked authoritative attempt performed zero DB/filesystem mutation and created no production recovery root.
- Primary classification: `DESIGN_GAP`.
- Secondary classification: test-fixture topology drift. Existing historical tests flatten six evidence files into one root, while the real consumed run produced two immutable evidence roots.

The repair must not copy, move, symlink, or rewrite historical evidence merely to satisfy the current validator.

## Proven cause

`_historical_validate_artifacts()` currently resolves every entry in `HistoricalFourTokenRecoveryContract.expected_artifact_sha256` as `artifact_root / name`.

The real historical topology is different:

Execution/historical artifact root owns:

- `terminal-summary.json`;
- the canonical historical campaign lease;
- the real pre-campaign backup and other execution evidence already present there.

The consumed application root owns the five application/wrapper artifacts:

- `application-marker.json`;
- `git-provenance-manifest.json`;
- `wrapper-terminal.json`;
- `child-terminal.json`;
- `child-stderr.txt`.

All six SHA-256 values are already pinned by the exact historical contract. The design error is location ownership, not evidence identity.

## Rejected remedies

### Copy the five files into the historical root

Rejected. This mutates original evidence, changes the historical root inventory, and converts a real two-root execution into a reconstructed layout.

### Build a merged authoritative root elsewhere

Rejected. The authoritative campaign lease path is durably bound to the real execution root. A merged root would either fail the canonical lease invariant or require the disposable-only lease override, which is not appropriate for authoritative reconciliation.

### Weaken or remove artifact validation

Rejected. Hash-pinned consumed-application evidence is required to prove the exact historical execution and original terminal cause.

### Generic path resolver/free-form artifact map

Rejected. This one-off recovery must remain exact and fail closed, not become a generic filesystem indirection surface.

## Approved repair shape

Keep `artifact_root` as the canonical execution root and lease owner.

Add one explicit read-only `application_artifact_root` input to the exact historical reconciliation boundary. It exists only to point at the already-existing consumed application evidence root.

The validator must preserve the existing six SHA pins but resolve them by fixed ownership:

- execution root: `terminal-summary.json`;
- application root: the five application/wrapper artifacts listed above.

No artifact is copied, moved, rewritten, deleted, or generated by validation.

`application_artifact_root` must never influence:

- DB selection;
- pre-campaign backup selection;
- lease selection/release;
- recovery-root creation;
- Scheduler ownership;
- discovery ownership;
- migration behavior;
- runtime/source execution.

The authoritative lease continues to resolve only from `artifact_root/campaign.lease.lock`, with `lease_lock_path_override` omitted.

## Exact root binding required before implementation

Implementation is blocked until a fresh read-only local audit records the full resolved consumed application-root path and proves:

1. all five required application artifacts exist there;
2. each full SHA equals the existing contract value;
3. `terminal-summary.json` remains sourced from the historical execution root;
4. historical execution root and consumed application root listings are unchanged before/after inspection;
5. authoritative DB SHA remains exactly `5e830af4...` and no SQLite sidecars are created;
6. original lease SHA remains unchanged;
7. no Printer process/runtime is started.

The root path must be supplied untruncated. Do not guess or infer it from naming conventions.

## Production interface design

The exact function should gain an explicit argument before optional test/runtime hooks, conceptually:

```python
reconcile_exact_historical_four_token_execution(
    *,
    operator_approved: bool,
    current_db: str | Path,
    pre_campaign_backup: str | Path,
    artifact_root: str | Path,
    application_artifact_root: str | Path,
    recovery_root: str | Path,
    contract: HistoricalFourTokenRecoveryContract | None = None,
    ...,
)
```

The exact private artifact validator should receive both resolved roots. Use fixed artifact-name ownership; do not allow arbitrary filename-to-path mappings.

The existing `expected_artifact_sha256` values may remain the single hash map to minimize contract churn. Root ownership should be explicit constants/sets for this exact historical execution.

The helper `historical_four_token_reconciliation_paths()` must not guess a consumed application root. Either leave that value absent until the exact local path is bound, or add it only after the read-only binding audit proves the exact path. Authoritative operator calls must continue passing the real DB path explicitly when importing from a detached worktree.

## Fail-closed requirements

Before any write, reject if:

- either required root is missing/unreadable;
- any required artifact is absent;
- any SHA mismatches;
- an application-owned artifact is only present in the execution root but absent from the supplied application root;
- `terminal-summary.json` is absent from the execution root;
- terminal-cause payload checks fail;
- DB/lease/process/ownership/pre-state gates fail.

The consumed application root must be read-only from the recovery operation. Its complete file inventory/hashes must remain unchanged after success or failure.

## Minimum TDD/proof plan

RED first against the current implementation:

1. two-root exact historical fixture is rejected because the five application artifacts are not under `artifact_root`;
2. no DB or lease mutation occurs on that rejection.

GREEN requirements:

1. exact two-root fixture reconciles the proven ten DB identities;
2. application root remains byte-for-byte unchanged;
3. historical execution root changes only by canonical lease deletion plus fresh recovery evidence outside that root;
4. missing/wrong-hash application artifact rejects before mutation;
5. missing/wrong-hash execution `terminal-summary.json` rejects before mutation;
6. wrong supplied application root rejects before mutation;
7. normal authoritative path still omits `lease_lock_path_override`;
8. disposable proof uses separate disposable copies of both roots and the disposable-only lease override;
9. idempotent replay remains zero-write;
10. existing discovery-batch, lease-path, and historical reconciliation focused regressions remain green.

Verification scope: changed tests + nearest historical recovery/lease/discovery contract tests + `py_compile` + diff checks. No broad suite unless a major closeout gate requires it. Preserve unrelated pre-existing failures as baseline facts.

## Authoritative operation after repair

Do not resume authoritative reconciliation immediately after implementation.

Required sequence:

1. exact application-root binding audit;
2. focused RED/GREEN implementation;
3. implementation closeout;
4. fresh disposable two-root proof using byte-identical DB and separate copied evidence roots;
5. proof closeout;
6. fresh authoritative readiness review;
7. separately approved bounded authoritative reconciliation.

No step may reuse the blocked authoritative attempt as authorization to mutate.

## Process-probe note

The blocked attempt also proved that heredoc/parent-shell command lines containing the execution ID can trigger the conservative default live-process probe. This is an operator invocation artifact, not the current repair target. Future local proof/authoritative invocations should use a script file or another command form whose ancestor argv does not contain the historical execution ID. Do not weaken the production live-process guard in this lane.

## Money-usefulness contribution

This preserves truthful historical evidence topology while allowing the abandoned durable ownership to be reconciled through the exact canonical recovery path. It improves corpus/lifecycle trustworthiness without creating trading capability.

## What this improves

- evidence ownership matches the real consumed run;
- no reconstructed historical artifact layout is required;
- authoritative lease identity remains strict;
- the exact six artifact hashes stay mandatory;
- future disposable and authoritative proofs can exercise the real two-root topology.

## What remains locked

This design does not authorize authoritative reconciliation, source fetching, discovery/runtime/Scheduler execution, memory generation, another campaign, six-token widening, longer windows, retrieval, paper decisions, BUY/SELL/HOLD, positions, trade events/audits, PnL, wallets, private keys, real funds, scoring/ranking/confidence/weighted logic, embeddings/vectors, or paid APIs.

## Functionality Risks / Setbacks / Efficiency Blockers

- The exact consumed application-root path is not yet recorded in the remote evidence and must be bound read-only before implementation.
- Tests previously flattened evidence topology; they must be corrected without weakening hash or terminal-cause checks.
- Any proposal to copy evidence into the execution root would destroy the invariant this repair is meant to preserve.
- The authoritative DB remains stranded until the full repair/proof/readiness/operation sequence completes.
- The historical operation remains state-specific and must not become a generic recovery mechanism.
